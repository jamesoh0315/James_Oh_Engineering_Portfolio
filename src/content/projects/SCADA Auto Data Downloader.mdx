At **Dometic Marine**, production data lives on the SCADA machine network while the
Power BI reporting that depends on it lives on the office network. Somebody had to carry
the data across by hand, every day. I built the tool that does it on a schedule instead,
then rebuilt the interface around it.

## Overview

### The Problem

Inspection results, attainment figures, and machine tag history are all recorded on the
machine network. The analyst who owned the Power BI reporting had no automated route to
any of it, so every refresh started with a person opening a downloader, picking a date
range, and exporting the datasets one at a time.

That was repetitive, and it capped how current the reports could be. They were only ever
as fresh as the last time someone remembered to run the export.

A downloader already existed and worked, but everything sat on a single window. Every
button repeated the phrase `from database to "C:\output"`, which pushed the actual dataset
name to the end where it was hardest to scan. A raw OPC tag list, the database picker, and
the table picker all competed for the same screen.

## Automating the download

The automated job runs on the **IT gateway PC**, the one machine that can see both
networks, and pulls a configurable window of history into `C:\output` every night at
**3:00 AM**. Most of the work was in the details that decide whether an unattended job is
actually trustworthy.

- **A timer script ticks every minute** and does nothing unless the hour is 3 and the
  minute is 0. Simple, and it means the job still fires correctly no matter when the
  client was last restarted.
- **The client gates itself on its own hostname.** At startup it checks which machine it
  is running on, enabling auto mode on the gateway PC and falling back to manual
  everywhere else. One project and one client covering both behaviours, rather than a
  separate build to keep in sync.
- **An overnight job must never wait on a dialog.** Every message box in the auto-download
  path was replaced with console output, since a popup at 3 AM would block the run until
  somebody dismissed it the next morning.
- **A reboot failsafe.** Ignition starts checkboxes unchecked, so if the gateway PC ever
  restarted, the downloader would have come back up with every dataset deselected and
  quietly stopped downloading, with no error to notice. The startup script now
  force-selects them.
- **The settings window is deliberately kept open.** It cannot be closed, and clicking
  outside it minimises it instead, because the timer script reads the schedule and the
  dataset selections directly off those components.

The settings tab exposes the parts an operator should control: an auto/off toggle, the
range of past data to pull, and which datasets are included. The range accepts anything
from 1 to 365 days, with a 30 day default.

## Rebuilding the interface

The manual downloader was still worth keeping for one-off pulls, so it was reorganised
rather than removed. One crowded window became **four tabs**: Quick Access, Tag History,
Database, and Auto-Download Settings.

Stating the `C:\output` destination once in a header, instead of on every button, let each
button shrink to just the name of the dataset it fetches. The same grid now reads at a
glance.

I also added a **generic database and table browser**. Rather than hardcoding another
button for every new dataset, it queries `INFORMATION_SCHEMA` to populate both pickers, so
tables added later show up on their own with no code change. The date range is bound as
query parameters.

Alongside that, the downloader's coverage was expanded with the end-of-line test datasets
(**HELM**, **EPS HELM**, **X30**, **X30 Fuel Pump**, **X30 Compressor**, **SPA**, and
**Pivot**) and scrap issue transactions.

## Outcome

Manual data retrieval is gone. The selected datasets land on the gateway PC every night at
3:00 AM, ready for Power BI to pick up, and the reporting no longer depends on somebody
remembering to run an export. The manual path is still there when a specific range is
needed, and it is considerably quicker to drive than it was.

Two things cost more time than the scripting did. The first was the **Ignition Designer
learning curve**, since the Vision module's scripting model and component hierarchy were
both new to me. The second was deployment: the gateway PC needed **selective auto-login**
configured so that the Vision client is actually running and logged in overnight. A
scheduled job is worth nothing if nothing is awake at 3 AM to run it.
